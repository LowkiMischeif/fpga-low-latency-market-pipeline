# What "AI" means in this project

**Offline-tuned fixed-point weights, loaded into the hardware as configuration.
Nothing else.** No neural network, no learning or inference on the FPGA beyond one
weighted sum and two compares, and no claim that any policy here makes money.

## The policy the hardware runs

`rtl/policy_engine.sv`, header:

```
score = w0 + (w_spread*spread + w_imbalance*imbalance + w_momentum*momentum) >>> W_FRAC_W
BUY  if score >  theta_buy
SELL if score <  theta_sell
HOLD otherwise
```

Formats, all from `rtl/market_pkg.sv`:

| Quantity | Format | Constant |
|---|---|---|
| `w_spread`, `w_imbalance`, `w_momentum` | signed Q3.12 | `W_W`, `W_FRAC_W` |
| `w0` | signed integer, score units | `W_W` |
| `theta_buy`, `theta_sell`, score | signed integer, saturating | `SCORE_W` |
| spread, momentum | signed, Q14.2 ticks | `SPREAD_W`, `MOM_W`, `PRICE_FRAC_W` |
| imbalance | signed Q1.14 | `IMB_W`, `IMB_FRAC_W` |

The features keep their natural units and each weight absorbs the scaling, so the
datapath has no normalising divide or shift. Every accumulation saturates
(`score_sat_add` in `rtl/market_pkg.sv`): a wrapped sum would turn a strong sell
into a strong buy.

## Where the weights come from

`scripts/train_policy.py` is a seeded random search over `w0`, the three weights
and the two thresholds, scored on a replay of a generated trace.

- **The search scores quantised candidates.** Each draw is rounded to the formats
  above before it is scored, and scored with a bit-exact integer mirror of the RTL
  (`rtl_score` and `decide` in `scripts/train_policy.py`). A float search quantised
  afterwards could pick a policy whose hardware twin behaves differently.
- **The feature model mirrors `rtl/feature_engine.sv`**, including the reciprocal
  table used for imbalance, so a weight sees offline the numbers it will see in
  hardware.
- **The risk limits are not searched.** `max_long`, `max_short`, `max_order_qty`,
  `max_spread` and `kill` are passed through unchanged (`as_policy` in
  `scripts/train_policy.py`). A tuner that could relax its own position cap to
  score better would defeat the risk gate.

### The objective is synthetic

`score_policy` in `scripts/train_policy.py` rewards decisions that agree with the
next midprice move on the same symbol and subtracts a fixed penalty per trade. A
policy that never trades is refused outright. The objective exists to make
different weights produce visibly different behaviour. **It is not profit and
loss**, and nothing in this repository presents it as one.

## The two committed policies

| Policy | Origin | File |
|---|---|---|
| `baseline` | **Hand-chosen, not trained.** Spread-led, on a different signal from the tuned policy, so the two differ in kind rather than being two tuner outputs. The file's `note` says so. | `tb/configs/baseline.json` |
| `tuned` | Generated by the exact command recorded in the file's `note`. A test reruns that command. | `tb/configs/tuned.json` |

## From weights to hardware

1. `scripts/export_config.py` quantises a policy JSON to the package formats. It
   reads every width and register address out of `rtl/market_pkg.sv` at run time
   and **refuses** a value that does not fit rather than letting it wrap.
2. It writes two forms of the same register-write sequence, ending in `CFG_COMMIT`:
   - `tb/configs/*.cfg`, which `tb/tb_policy_configs.sv` and
     `tb/tb_market_pipeline_top.sv` replay as the ground truth;
   - `rtl/mem/rom_cfg_*.mem`, the ROM images `rtl/cfg_loader.sv` writes into
     `rtl/config_regs.sv` on reset release and whenever `sw[0]` changes.
   `scripts/test_mem_files.py` fails if a committed `.mem` differs from what the
   tool writes for the committed JSON.
3. `rtl/config_regs.sv` holds writes in a shadow copy until `CFG_COMMIT`, so a batch
   lands together. `rtl/policy_engine.sv` then snapshots the whole active
   configuration on the edge it accepts each event, so every decision is scored by
   exactly one configuration.

## What configuration can and cannot change

Configuration reaches the adder tree and the risk compares only. No weight,
threshold or limit appears in any valid, ready or enable expression, so a policy
changes **what** the pipeline decides and never **when**. `tb/tb_policy_configs.sv`
runs the same trace under both committed policies and requires the two latency
histograms to be identical; see `docs/LATENCY.md` for the measured result.
